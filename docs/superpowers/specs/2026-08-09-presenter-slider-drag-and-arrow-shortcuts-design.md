# 主持滑杆拖窗冲突与方向键设计

**日期：** 2026-08-09  
**目标版本：** Connection Prompter 1.2.1

## 背景与根因

主持浮窗为了让用户能从空白处移动窗口，设置了
`isMovableByWindowBackground = true`。当前速度控件使用 SwiftUI `Slider`；在实际命中的
`NSHostingView` 上，AppKit 的 `mouseDownCanMoveWindow` 为 `true`，所以滑杆的连续横向拖动会同时触发窗口移动。

本地 AppKit 探针确认：即使原生 `NSSlider.mouseDownCanMoveWindow` 为 `false`，macOS 26 的 SwiftUI 宿主层仍会先触发系统背景拖窗。三种控件级排除实现都在真实拖拽测试中产生相同的 35 点窗口位移，因此必须关闭系统自动背景拖窗，并显式划定可拖区域。

## 已确认的需求

- 拖动速度滑杆只改变自动滚动速度，不移动浮窗。
- 拖动浮窗其他空白区域仍能移动浮窗。
- 主持浮窗显示、应用接收键盘输入且当前没有编辑文字时：
  - `←` 每次降低速度 `0.1`。
  - `→` 每次提高速度 `0.1`。
  - `↑` 执行上一页/向上导航。
  - `↓` 执行下一页/向下导航。
- 保留 `Space` 下一页和现有全局快捷键 `⌥⌘←`、`⌥⌘→`。
- 速度继续限制在 `0.1...3.0`，并沿用现有的取整、保存和实时显示逻辑。

## 方案

### 1. 使用显式正文拖窗隔离工具栏

关闭 `NSPanel.isMovableByWindowBackground`，避免系统在 SwiftUI 控件处理事件之前移动窗口。保留现有 SwiftUI `Slider`、68 点宽度、mini 尺寸、连续更新、辅助功能信息和 0.1 步进。

专用 `PresenterPanel` 在 `sendEvent(_:)` 中检查鼠标按下位置：顶部 50 点属于工具栏交互区，外围 6 点保留给窗口缩放；其余正文/背景区域调用 `NSWindow.performDrag(with:)`。这条路径发生在 SwiftUI 事件分发之前，因此工具栏内任何控件都不会带动窗口，正文和背景空白仍可移动浮窗。

`NSHostingView` 使用从顶部向下增长的翻转坐标系，因此显式拖动条件为 `location.y > 50`，而不是按普通 AppKit 底部原点计算。

窗口缩放、位置记录、People View、鼠标穿透和辅助功能路径保持不变。

### 2. 在现有本地键盘路由中增加左右键

沿用 `PresenterPanelController` 的本地按键监控，不注册无修饰方向键为系统全局热键。这样不会抢占其他应用中的方向键。

当主持浮窗未显示、存在任意修饰键，或文字编辑器正在接收输入时，事件原样传回系统。符合主持条件时，左/右键调用现有速度调整入口，上/下键继续调用上一页/下一页入口；已处理事件不再向下传播。

## 测试设计

1. 扩展主持界面测试，使用真实坐标从滑杆左侧拖到右侧：
   - 速度实时数值必须提高。
   - 拖动前后主持浮窗的 `x`、`y` 坐标必须保持不变（允许最多 1 点测量误差）。
2. 在主持浮窗中发送无修饰 `←/→`，验证速度按 0.1 改变并可恢复。
3. 记录文稿元素的屏幕位置，发送 `↓` 后确认文本移动，再发送 `↑` 确认返回。
4. 运行全部单元测试与 UI 测试，确认拖窗、People View、自动滚动、恢复会话等既有流程不回归。
5. 用 Release 配置构建 1.2.1（build 4），检查签名、沙盒权限、arm64 架构和 ZIP 完整性。

## 非目标

- 不改变速度范围、步进或自动滚动算法。
- 不改变工具栏布局和视觉样式。
- 不把无修饰方向键注册为跨应用全局快捷键。
- 不改变窗口尺寸约束、位置持久化或缩放行为。

## 完成标准

- 物理拖动滑杆能稳定调速，浮窗不发生位移。
- 空白处仍可移动浮窗。
- 四个无修饰方向键按已确认的映射工作，且不影响文字编辑和其他应用。
- 完整自动化测试通过，并交付不覆盖 1.2 的 `Connection Prompter 1.2.1.app` 与 ZIP。
